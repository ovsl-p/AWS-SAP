# 共有サービス VPC にはつなぎ、部門の VPC 同士は分ける

- 出典：CloudTech SAP-2008（カテゴリ：分野1-ネットワーク接続戦略）
- 日付：2026-11-14
- 分野：1 アーキテクチャ設計（タスク 1.4 ネットワーク）
- 自分の解答：1番目（正解）
- 関連：[専用線を足してもネット経路を変えない](専用線を足してもネット経路を変えない.md)（Transit Gateway が不要だったケース）

## 問題の要約（自分の言葉で）

1つのリージョンに、事業部門ごとの VPC が20個ある。どれも共有サービス VPC（認証、ログ収集）にはつなぎたい。
部門の VPC 同士は通信させず、監査の面でもネットワークで遮断したい。今後は数十個単位で増えるので、増えるたびに個別の接続設定はしたくない。

## 要件のキーワード

- 「VPC が20個、数十個単位で増える」→ **Transit Gateway**（VPC がたくさんある）
- 「部門同士は遮断」→ **Transit Gateway のルートテーブルを分ける**（セグメンテーション）
- 「監査上も遮断」→ セキュリティグループ頼みではなく、**そもそも経路がない** 状態にする

## 正解

- 1番目：Transit Gateway に全 VPC をアタッチし、ルートテーブルを2つ作る
  - **部門用**：共有サービス VPC へのルートだけ → 部門の VPC はここに関連付け
  - **共有サービス用**：全部門の VPC へのルート → 共有サービス VPC はここに関連付け

## なぜ他はダメ？

| 選択肢（要点） | ダメな理由 |
| --- | --- |
| 2番目：共有サービス VPC と各部門 VPC を VPC ピアリングでつなぐ | 部門同士はピアリングしなければ通信できないので、遮断はできる。でも **VPC が増えるたびにピアリングを個別に作る** ことになり、「個別設定を積み上げない」に反する |
| 3番目：Transit Gateway の1つのルートテーブルに全部入れ、セキュリティグループと NACL で遮断 | ネットワークの経路としては **全部つながってしまう**。遮断を VPC ごとのセキュリティグループや NACL に任せると、設定漏れが起きやすく監査でも説明しにくい |
| 4番目：GWLB エンドポイントや PrivateLink で共有サービスにつなぐ | GWLB はファイアウォールなどの **アプライアンスを挟む** ためのもの。PrivateLink はサービス単位の接続で、認証基盤やログ基盤のように「VPC 全体とつなぐ」用途には合わない |

## 一言で言うと

- VPC がたくさん ＋ つなぐ相手を選びたい → **Transit Gateway ＋ ルートテーブルを分ける**
- 「遮断」は経路で切る。セキュリティグループ頼みは監査に弱い
